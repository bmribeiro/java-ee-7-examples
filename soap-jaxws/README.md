# Java EE 7 - SOAP / JAX-WS Example

Small SOAP web service built with **Java EE 7** and **JAX-WS**.

The example exposes customer operations through SOAP, uses JAXB for XML mapping, delegates the application logic to a stateless EJB and demonstrates how application errors can be exposed as SOAP Faults.

## Stack

- Java 8
- Java EE 7
- JAX-WS
- JAXB
- EJB
- Maven
- GlassFish 4.1.2
- SOAP 1.1
- WSDL

                            │   └── Customer.java

The service follows a simple layered structure:

```text
SOAP Request
     |
     v
CustomerSoapService
     |
     | @EJB
     v
CustomerService
     |
     v
In-memory storage
```

`CustomerSoapService` is responsible for the SOAP contract and delegates the actual operations to `CustomerService`.

The current implementation stores customers in memory. This is intentional so that the example stays focused on JAX-WS and SOAP.

## SOAP endpoint

After deployment on GlassFish, the service is exposed under the `soap-jaxws` application context.

The generated WSDL can normally be accessed at:

```text
http://localhost:8080/soap-jaxws/CustomerSoapService?wsdl
```

The exact endpoint URL generated by the application server should be confirmed through the deployed WSDL.

The WSDL is the authoritative contract for the SOAP service.

## Service namespace

The service uses the following target namespace:

```text
http://soap.examples.brunoribeiro.pt/customer
```

It is configured in the JAX-WS endpoint:

```java
@WebService(
        serviceName = "CustomerService",
        portName = "CustomerServicePort",
        targetNamespace = "http://soap.examples.brunoribeiro.pt/customer"
)
```

## GetCustomer

Returns a customer by ID.

The Java operation is exposed with:

```java
@WebMethod(operationName = "GetCustomer")
```

### Request

Example request for customer `1`:

```xml
<?xml version="1.0" encoding="UTF-8"?>

<soapenv:Envelope
        xmlns:soapenv="http://schemas.xmlsoap.org/soap/envelope/"
        xmlns:cust="http://soap.examples.brunoribeiro.pt/customer">

    <soapenv:Header/>

    <soapenv:Body>
        <cust:GetCustomer>
            <id>1</id>
        </cust:GetCustomer>
    </soapenv:Body>

</soapenv:Envelope>
```

### Response

A successful response contains the requested customer:

```xml
<soap:Envelope
        xmlns:soap="http://schemas.xmlsoap.org/soap/envelope/">

    <soap:Body>

        <GetCustomerResponse>

            <return>
                <id>1</id>
                <name>Bruno</name>
                <email>bruno@example.com</email>
            </return>

        </GetCustomerResponse>

    </soap:Body>

</soap:Envelope>
```

The exact XML namespace prefixes and generated wrapper elements may differ depending on the WSDL generated by GlassFish.

## SOAP Faults

Unlike the REST example, where application errors are represented through HTTP status codes such as `404 Not Found`, SOAP can expose structured errors through SOAP Faults.

This example defines:

```text
CustomerNotFoundFault
```

for requests referencing a customer that does not exist.

The exception is declared as a JAX-WS Web Fault:

```java
@WebFault(name = "CustomerNotFoundFault")
public class CustomerNotFoundException extends Exception {
}
```

The fault contains structured information represented by `CustomerFault`:

```text
CustomerFault
├── code
└── message
```

### Customer not found

For example, requesting:

```text
GetCustomer(999)
```

results in a SOAP Fault instead of returning `null`.

Representative response:

```xml
<soap:Envelope
        xmlns:soap="http://schemas.xmlsoap.org/soap/envelope/">

    <soap:Body>

        <soap:Fault>

            <faultcode>soap:Server</faultcode>

            <faultstring>Customer not found</faultstring>

            <detail>

                <CustomerNotFoundFault>

                    <code>CUSTOMER_NOT_FOUND</code>

                    <message>
                        Customer with id 999 was not found
                    </message>

                </CustomerNotFoundFault>

            </detail>

        </soap:Fault>

    </soap:Body>

</soap:Envelope>
```

The generated WSDL contains the fault definition as part of the service contract.

## JAXB model

SOAP messages are XML-based.

The `Customer` Java object is mapped to XML using JAXB annotations:

```java
@XmlAccessorType(XmlAccessType.FIELD)
@XmlType(
        name = "Customer",
        propOrder = {
                "id",
                "name",
                "email"
        }
)
public class Customer {
}
```

Conceptually:

```text
Java Customer
      |
      | JAXB
      v
XML Customer
```

JAX-WS uses this XML representation when creating SOAP request and response messages.

## EJB service

Business operations are separated from the SOAP endpoint.

`CustomerService` is implemented as a stateless EJB:

```java
@Stateless
public class CustomerService {
}
```

and injected into the endpoint:

```java
@EJB
private CustomerService customerService;
```

The endpoint therefore deals mainly with the SOAP contract:

```text
@WebService
@WebMethod
@WebParam
@WebFault
```

while the service handles customer operations and storage.

## Data storage

For simplicity, customer data is currently stored in memory using:

```java
ConcurrentHashMap<Long, Customer>
```

Customer IDs are generated using:

```java
AtomicLong
```

Data is lost when the application is restarted or redeployed.

Persistence is intentionally outside the scope of this module and can later be replaced by JPA without changing the SOAP contract significantly.

## WSDL

The WSDL describes the SOAP service contract, including:

```text
service
operations
messages
XML types
bindings
endpoint
faults
```

It is generated by JAX-WS from the Java endpoint and its annotations.

After deployment:

```text
http://localhost:8080/soap-jaxws/CustomerSoapService?wsdl
```

A SOAP client can use this WSDL to discover the available operations and generate client-side classes.

## WSDL vs OpenAPI

The `rest-jaxrs` example uses OpenAPI to describe its HTTP API.

This module uses WSDL because it exposes a SOAP service.

```text
REST / JAX-RS             SOAP / JAX-WS

OpenAPI                   WSDL
JSON                      XML
Swagger UI                SoapUI
HTTP status codes         SOAP Faults
```

For SOAP, the generated WSDL is the machine-readable service contract.

## Building

From the root of the multi-module project:

```bash
mvn clean package
```

To build only this module:

```bash
mvn -pl soap-jaxws clean package
```

After a successful build:

```text
BUILD SUCCESS
```

the WAR is generated at:

```text
soap-jaxws/target/soap-jaxws.war
```

## Deploying on GlassFish

Start GlassFish if it is not already running:

```bat
C:\glassfish4\glassfish\bin\asadmin.bat start-domain
```

Deploy the application:

```bat
C:\glassfish4\glassfish\bin\asadmin.bat deploy soap-jaxws\target\soap-jaxws.war
```

To redeploy an existing deployment:

```bat
C:\glassfish4\glassfish\bin\asadmin.bat deploy --force=true soap-jaxws\target\soap-jaxws.war
```

The deployed applications can also be inspected through the GlassFish Admin Console:

```text
http://localhost:4848
```

## Testing with SoapUI

SoapUI can import the generated WSDL and create SOAP requests automatically.

Create a SOAP project using:

```text
http://localhost:8080/soap-jaxws/CustomerSoapService?wsdl
```

SoapUI should discover operations similar to:

```text
CustomerService
├── GetCustomer
└── CreateCustomer
```

The generated request templates can then be edited and executed against the local GlassFish server.

Testing `GetCustomer` with an unknown ID is also a simple way to verify the `CustomerNotFoundFault`.

## Notes

This project follows a code-first approach: the Java classes and JAX-WS annotations define the service and GlassFish generates the WSDL during deployment.

For a production SOAP integration, the opposite approach is also common: starting from an existing WSDL/XSD contract and generating the Java classes from that contract.

The current example intentionally stays small so the focus remains on the Java EE 7 SOAP stack rather than persistence or infrastructure.

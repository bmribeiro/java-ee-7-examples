Java EE 7 - SOAP / JAX-WS Example

Small SOAP web service built with Java EE 7 and JAX-WS.

The example exposes customer operations through SOAP, uses JAXB for XML mapping, delegates application logic to a stateless EJB, and demonstrates how application errors can be exposed as SOAP Faults.

In-memory storage

CustomerSoapService defines the SOAP endpoint and delegates customer operations to CustomerService.

The current implementation stores customers in memory so the example remains focused on JAX-WS, JAXB, WSDL and SOAP Faults.

SOAP endpoint

After deployment on GlassFish, the service is published at:

http://localhost:8080/soap-jaxws/CustomerService

The generated WSDL is available at:

http://localhost:8080/soap-jaxws/CustomerService?wsdl

GlassFish also exposes a simple built-in tester:

http://localhost:8080/soap-jaxws/CustomerService?Tester

The Java implementation class is:

pt.brunoribeiro.examples.soap.endpoint.CustomerSoapService

while the published service name is CustomerService.

This comes from the endpoint configuration:

@WebService(
serviceName = "CustomerService",
portName = "CustomerServicePort",
targetNamespace = "http://soap.examples.brunoribeiro.pt/customer"
)

The WSDL is the authoritative machine-readable contract for the SOAP service.

SOAP Faults

Unlike the REST example, where application errors are commonly represented through HTTP status codes such as 404 Not Found, SOAP can expose structured application errors through SOAP Faults.

This example defines:

CustomerNotFoundFault

for requests referencing a customer that does not exist.

The exception is exposed as a JAX-WS Web Fault:

@WebFault(name = "CustomerNotFoundFault")
public class CustomerNotFoundException extends Exception {
}

The structured fault data is represented by CustomerFault:

CustomerFault
├── code
└── message

Customer not found

For example:

GetCustomer(999)

results in a SOAP Fault instead of returning null.

Representative response:

<soap:Envelope
xmlns:soap="http://schemas.xmlsoap.org/soap/envelope/">

    <soap:Body>

        <soap:Fault>

            <faultcode>soap:Server</faultcode>
            <faultstring>Customer not found</faultstring>

            <detail>

                <CustomerNotFoundFault>
                    <code>CUSTOMER_NOT_FOUND</code>
                    <message>Customer with id 999 was not found</message>
                </CustomerNotFoundFault>

            </detail>

        </soap:Fault>

    </soap:Body>

</soap:Envelope>

The generated WSDL contains the fault definition as part of the service contract.

JAXB model

SOAP messages are XML-based. The Customer Java object is mapped to XML with JAXB annotations:

@XmlAccessorType(XmlAccessType.FIELD)
@XmlType(
name = "Customer",
propOrder = {
"id",
"name",
"email"
}
)
public class Customer {
}

|
| JAXB

JAX-WS uses this mapping when serializing and deserializing SOAP messages.

EJB service

Business operations are kept separate from the SOAP endpoint.

CustomerService is implemented as a stateless EJB:

@Stateless
public class CustomerService {
}

and injected into the endpoint:

@EJB
private CustomerService customerService;

The endpoint deals mainly with the SOAP contract, while the service handles customer operations and storage.

Data storage

For simplicity, customer data is stored in memory using:

ConcurrentHashMap<Long, Customer>

Customer IDs are generated using:

AtomicLong

Data is lost when the application is restarted or redeployed.

Persistence is intentionally outside the scope of this module and can later be replaced with JPA without significantly changing the SOAP contract.

WSDL vs OpenAPI

The rest-jaxrs module uses OpenAPI to document its HTTP API. This module uses WSDL because it exposes a SOAP service.

REST / JAX-RS             SOAP / JAX-WS

OpenAPI                   WSDL
JSON                      XML
Swagger UI                SoapUI
HTTP status codes         SOAP Faults

For SOAP, the WSDL is the machine-readable service contract.

Build

From the root of the Maven multi-module project:

mvn clean package

To build only this module:

mvn -pl soap-jaxws clean package

After a successful build, the WAR is generated at:

soap-jaxws/target/soap-jaxws.war

Deploy on GlassFish

Start GlassFish if it is not already running:

C:\glassfish4\glassfish\bin\asadmin.bat start-domain

Deploy the application:

C:\glassfish4\glassfish\bin\asadmin.bat deploy soap-jaxws\target\soap-jaxws.war

To redeploy an existing deployment:

C:\glassfish4\glassfish\bin\asadmin.bat deploy --force=true soap-jaxws\target\soap-jaxws.war

The GlassFish Admin Console is available at:

http://localhost:4848

For this deployment, GlassFish reports:

Service Name:        CustomerService

Endpoint Address:    /soap-jaxws/CustomerService

Notes

This example follows a code-first approach: Java classes and JAX-WS annotations define the service, and GlassFish generates the WSDL during deployment.

A contract-first approach is also common in enterprise SOAP integrations, where development starts from an existing WSDL/XSD and Java classes are generated from that contract.

The example intentionally stays small so the focus remains on the Java EE 7 SOAP stack rather than persistence or infrastructure.
